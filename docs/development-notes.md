## 当前决定

用户目前的材料数量不大，暂不进行大列表性能优化。继续使用现有界面和功能，等实际使用中出现卡顿再评估。本文记录问题和测试依据，方便以后接着开发；所列方案尚未实现。

## 已完成的功能与偏好

- 软件名为「归序 · TidyDrop」，面向 Windows，采用 React + TypeScript 界面和 C# 文件处理核心。
- 用户偏好柔和雾白界面，避免大面积绿色或高亮纯白。
- 拖入桌面快捷方式后，在已配置归档位置且开启自动整理时，后台收纳，不打开或抢焦点。双击入口打开归档空间。
- 日期视图采用按天排列的时间线，类型视图采用分类卡片；日期和类型支持组合筛选，切换视图保留筛选与搜索条件。
- v0.5.2 将两种视图改为约 500 毫秒的整块横向滑动：切到类型时旧内容向左滑出、新内容从右进入，切回日期时反向；选中按钮背景同步放慢。快速连续点击以最后选择为准。系统启用减少动态效果时直接切换，旧运行环境使用横向滑入兼容效果。这是视觉过渡，不包含大列表性能优化。
- 「打开位置」打开材料所在的资源管理器文件夹并选中它。已实际验证文件与文件夹，以及中文、空格、逗号名称。
- 文件夹作为一个项目整包收纳，保留内部结构。
- v0.6.0 新增 Windows 11 x64 一级右键菜单「复制文件路径」，支持文件、文件夹及多选，无引号，每行一个路径。设置里可添加、移除。使用独立原生组件与本地签名身份包，详见 [右键菜单说明](context-menu.md)。
- v0.5.0 已加入持久化材料清单：正常启动读取已保存清单，收纳和撤销更新条目，手动「刷新」核对目录。清单缺失、损坏或操作中断时扫描恢复，详见 [存储与材料清单说明](storage-and-catalog.md)。这项改进不包含大列表的行渲染优化。

实际存储层级为：

```text
用户选择的总文件夹/归序/年月/收纳日期/类型/材料
```

日期取收纳当天的本地日期。日期与类型视图使用同一份材料，不生成两套副本。

## 待观察的问题：大量材料时切换视图卡顿

当前界面会一次生成所有匹配材料行，没有分页或虚拟列表。切换视图不会重新扫描磁盘，但会重新进行筛选、统计、排序和界面渲染。

几千份材料全部展开时，模拟测试中已出现可感知的停顿。总材料量与当前显示的结果量需要分别考虑：即使总量较大，选择单个日期或类型后，显示的材料行可能较少。

### 本机模拟测试结果

| 材料数量 | 切到类型视图：中位数 | 切到日期视图：中位数 | 全部切换样本范围 |
| ---: | ---: | ---: | ---: |
| 100 | 29 ms | 45 ms | 25–249 ms |
| 1,000 | 175 ms | 247 ms | 170–253 ms |
| 5,000 | 738 ms | 851 ms | 698–883 ms |
| 10,000 | 1,415 ms | 1,479 ms | 1,303–1,591 ms |

100 份材料的第一次类型切换为 249 ms，后两次为 25–29 ms；不能只用热身后的结果代表首次切换。

测试方式与边界：

- 使用当前界面的独立测试副本，在本机 WebView2 中运行，没有修改在用软件或移动真实材料。
- 注入模拟归档记录，分布在六种类型。100 份覆盖 100 个收纳日，其余规模覆盖 365 个收纳日。
- 不设置日期、类型或搜索限制，一次显示全部匹配材料；两个方向各切换三次。
- 从模拟点击开始计时，包含界面更新、同步布局及两次渲染帧等待。测试窗口位于屏幕外，结果不等同于人眼测得的显示延迟。
- 不包含真实磁盘扫描、文件内容读取、移动或撤销的耗时。
- 结果仅代表本机、这个数据分布和 v0.4.0，不能作为其他电脑或后续版本的性能保证。

原始样本见 [performance-v0.4.0.json](performance-v0.4.0.json)。本次临时测试工具位于本地 `artifacts/prepare_performance.py` 和 `artifacts/performance-source/`，未纳入源码仓库；后续复测需重新准备工具或使用仍保留的本地副本。

### 代码中的主要开销

入口：[ArchiveBrowser.tsx](../frontend/src/ArchiveBrowser.tsx)。

1. 日期和类型页面都对全部可见材料生成 `ArchiveRow`；一万份材料会产生十余万个 DOM 元素。
2. 日期计数、判断日期是否有结果，以及每一天的材料分组，会反复遍历数组。日期越多，重复遍历越明显。
3. 筛选、排序、分类计数和日期标签计算大多在组件渲染期间执行，缓存范围有限。

v0.5.0 的原生清单读取入口为 [MainWindow.xaml.cs](../src/TidyDrop.App/MainWindow.xaml.cs) 中的 `RefreshLibrary`，默认经 `ArchiveCatalog.Load` 读取清单。首次建立、修复及手动更新才调用实际扫描逻辑 [ArchiveLibrary.cs](../src/TidyDrop.Core/ArchiveLibrary.cs)。未来应分别测量「正常启动读取清单」「首次建立或手动更新清单」与「已加载材料后切换视图」，避免把两个问题混为一谈。

## 未来出现问题时，如何继续

先记录实际症状：归档项目数量、收纳日数量、当前筛选条件、卡顿发生在启动/刷新/切换/搜索/滚动中的哪一步，以及大致持续时间。文件夹数量指整包项目数量，不把内部所有文件算成独立列表行。

建议根据测量结果按以下顺序处理：

1. **减少重复计算**：一次遍历建立日期与类型的分组和数量，缓存与材料及筛选条件相关的结果，避免按每个日期再次遍历整个列表。
2. **限制实际渲染的行数**：采用只渲染屏幕附近材料的虚拟列表，或先实现分批加载。日期时间线应连同日期标题一起处理，避免仍一次渲染所有日期下的材料。
3. **按实际瓶颈补充处理**：如果搜索仍阻塞输入，再考虑延后结果更新或后台计算。v0.5.0 已实现持久化清单；如果以后清单读取或手动目录核对成为瓶颈，再评估更适合的索引存储格式或目录增量核对。当前测试不足以证明这些额外工作现在必需。

优化时需要保留的行为：

- 日期与类型组合筛选、切换时保留条件、清除筛选和空结果提示。
- 搜索覆盖全部材料，分类数量统计完整结果，不随当前加载的行数变化。
- 每份材料的「打开位置」仍对应正确项目，文件夹仍作为完整项目显示。
- 不改变现有归档层级，不为不同视图复制材料，不影响整理记录、校验和撤销。
- 保留雾白配色，以及用户已认可的时间线和分类卡片布局。

复测建议：使用相同的 100 / 1,000 / 5,000 / 10,000 份模拟记录，比较两个方向的切换、搜索、滚动与首次加载；补充跨更多收纳日、单日大量材料、筛选后少量结果等分布。记录首次与后续操作耗时，并运行已有界面联动检查，核对筛选、数量和打开位置。改进幅度应由实测确认。
